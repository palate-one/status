# Blacksmith형 Palate 상태 페이지 디자인

## 목표

`status.blacksmith.sh`의 높은 스캔성을 참고하되 Palate 브랜드, GitHub 기반 공지, Worker/D1 무료 운영 구조를 유지한다. 사용자는 첫 화면에서 전체 상태, Web/API 상태, 최근 30일 가동률을 한 흐름으로 읽고 이어서 장애·점검 이력을 날짜순으로 확인할 수 있어야 한다.

## 선택한 방향

Blacksmith의 정보 구조를 Palate에 맞게 단순화한다.

- 상단에 큰 전체 상태 배너를 둔다.
- Web과 API를 각각 한 행으로 표시하고 행 안에 상태, 30일 가동률, 일별 rail을 함께 둔다.
- 서비스가 두 개뿐이므로 접기 그룹은 만들지 않는다.
- 진행 중인 장애와 예정 점검은 상태 영역 바로 아래에 먼저 노출한다.
- 종료된 장애와 완료된 점검은 날짜별 공개 운영 이력으로 묶는다.
- Blacksmith의 구독, Report an issue, 외부 상태 페이지 SaaS 기능은 추가하지 않는다.

## 검토한 대안

1. 선택: Blacksmith 정보 구조 + Palate 시각 언어. 스캔성이 가장 좋고 기존 데이터 계약을 그대로 사용할 수 있다.
2. 기존 화면 유지 + 큰 배너만 추가. 변경량은 작지만 구성 요소와 uptime이 떨어져 있어 핵심 개선이 약하다.
3. Instatus 같은 호스팅 서비스 사용. GitHub 공지, Worker/D1, 무조건 무료라는 운영 요구와 맞지 않는다.

## 화면 구조

### 헤더

- `Palate status` 브랜드와 `공개 운영 기록`만 유지한다.
- 데스크톱과 모바일 모두 얇고 단순한 한 줄 헤더를 사용한다.

### 전체 상태

- 읽기 폭 전체를 쓰는 상태 배너를 사용한다.
- 정상, 서비스 영향, 확인 불가 상태를 아이콘·문구·색상으로 함께 구분한다.
- 마지막 관측 시각 또는 다시 확인 안내를 같은 배너 안에 표시한다.

### 서비스별 uptime

- Web과 API 각각을 독립된 service row로 렌더링한다.
- 행 상단은 서비스명, 현재 상태, 30일 가동률을 표시한다.
- 행 하단은 30개의 동일 폭 세로 segment로 구성된 rail을 표시한다.
- segment는 정상, 문제 표본 존재, 관측 없음 상태를 구분한다.
- 각 segment의 접근성 이름은 날짜, 가동률, 정상·문제 표본 수, 측정 범위를 포함한다.
- rail 자체는 가로 스크롤하지 않는다. 320px에서도 화면 폭 안에 30개를 압축한다.

### 장애·점검과 이력

- 진행 중인 장애와 예정 점검을 별도 섹션으로 먼저 보여준다.
- 지난 기록은 해결·완료 시각 기준 최신 날짜부터 묶고 같은 날짜 안에서도 최신 기록을 먼저 표시한다.
- GitHub Markdown 본문과 기존 incident/maintenance schema를 그대로 사용한다.
- 데이터가 없으면 짧은 빈 상태 문구를 보여준다.

## 반응형

- 기준 viewport는 320px, 390px, 1280px다.
- 320px와 390px에서 수평 overflow가 없어야 한다.
- 모바일은 한 열, 데스크톱은 최대 읽기 폭 960px를 유지한다.
- 데스크톱에서도 30일만 표시한다. 무료 운영 범위와 기존 API 계약을 넓히지 않는다.

## 접근성

- heading은 H1 다음 H2, 하위 항목은 H3 순서를 지킨다.
- 상태를 색상만으로 구분하지 않는다.
- 작은 일반 텍스트는 흰 배경에서 최소 `4.5:1` 대비를 만족한다.
- focus-visible과 reduced-motion 지원을 유지한다.
- 상태 hydration 뒤 `aria-busy`를 `false`로 바꾸고 상태 문구는 polite live region으로 알린다.

## 데이터와 오류 처리

- `/api/status` 응답과 기존 `StatusViewModel`을 사용한다.
- API 오류, 빈 D1, stale 데이터는 정상으로 표시하지 않는다.
- 공개 화면과 브라우저 요청에 token, secret, account id, 사용자 식별자를 포함하지 않는다.
- 장애·점검 콘텐츠는 빌드 시 검증된 공개 Markdown만 렌더링한다.

## 테스트와 완료 기준

- view-model 테스트로 30개 segment의 label과 날짜별 이력 정렬을 검증한다.
- build 회귀 테스트로 heading 단계와 빈 데이터 markup을 검증한다.
- 기존 status-client 테스트로 정상·오류·stale hydration을 유지한다.
- focused tests, `bun run check`, `bun run build`, `git diff --check`를 통과한다.
- Orca 브라우저에서 320px, 390px, 1280px를 확인한다.
- 모바일·데스크톱 스크린샷, 수평 overflow 0, 콘솔 오류 0을 증거로 남긴다.

## 의도적 제외

- 외부 구독 채널, 이메일, Slack, Webhook
- 사용자 제보 폼
- 서비스 그룹 접기
- 90일 실시간 rail
- 새로운 데이터베이스나 SaaS
